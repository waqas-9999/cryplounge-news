# CrypLounge — Roles & Permissions

Reference for the access-control model: what every permission key means, which
role holds it by default, and how the check is actually performed.

**Source of truth:** `server/prisma/permissions.ts` — the catalogue and the
default grants. **Enforcement:** `server/src/modules/auth/guards/permissions.guard.ts`.

Every table below was generated by cross-referencing the catalogue against every
`@RequirePermissions(...)` in `server/src`, so "granted" and "actually enforced"
are reported separately. They are not the same thing.

---

## 1. How it works

Three pieces:

| Piece | Model | Role |
|---|---|---|
| `Permission` | one row per capability | the vocabulary of what *can* be granted |
| `RoleDefinition` | one row per role | the named bundle a user is assigned |
| `RolePermission` | join table | which keys a role actually holds |

Because grants live in the database, an administrator can change what a role may
do **without a deploy** — `permissions.ts` only supplies the starting point that
`npm run db:seed` writes.

### The check

A handler declares what it needs:

```ts
@Get('admin/analytics/overview')
@RequirePermissions('analytics.read')
overview(@Query() query: AnalyticsRangeQueryDto) { … }
```

`PermissionsGuard` then resolves it in this order:

1. No `@RequirePermissions` on the handler → **allowed** (subject to auth).
2. No authenticated user → `403 Authentication required`.
3. `user.role === 'SUPER_ADMIN'` → **allowed, unconditionally.**
4. Otherwise every declared key must be present in `user.permissions`, else
   `403 Missing permission: <keys>`.

Two consequences worth internalising:

- **Multiple keys on one handler are AND, not OR.** All must be held.
- **`SUPER_ADMIN` short-circuits before the grant list is consulted.** It is the
  break-glass role and cannot be locked out by a misconfigured grant — which is
  also why a permission missing from the catalogue silently becomes
  "SUPER_ADMIN only" rather than failing loudly. See §5.

## 2. Roles

Six system roles. `isSystem: true` on all of them, so they cannot be deleted.

| Key | Name | Intent |
|---|---|---|
| `SUPER_ADMIN` | Super Admin | Unrestricted, including role and permission changes |
| `ADMIN` | Admin | Full operational access; cannot alter permission grants |
| `EDITOR` | Editor | Creates, edits and publishes content across every section |
| `AUTHOR` | Author | Writes and edits content; submits for review rather than publishing |
| `MODERATOR` | Moderator | Reviews queued content without publishing rights |
| `VIEWER` | Viewer | Read-only access to the admin |

### The two distinctions that carry the model

**Author cannot publish.** Publishing is what makes content public, so it stays
with Editor and above. An Author holds `read`/`create`/`update` on every content
type but no `publish`, and `articles.service.ts:325` enforces this in the service
layer, not just at the route.

**Admin cannot change permissions.** `roles.manage` is held *only* by
`SUPER_ADMIN`. An Admin can invite and disable staff (`users.manage`) but cannot
escalate a role's grants — including their own. This is the boundary that stops
an Admin account compromise from becoming total.

## 5. Gaps found while writing this

Cross-referencing the catalogue against every `@RequirePermissions` in the
codebase surfaced four real discrepancies. They are listed here rather than
quietly fixed, because each changes who can do what.

### 5.1 Three permissions are enforced but do not exist — Organizers is locked

`organizers.controller.ts` guards four endpoints with keys that are **not in the
catalogue**:

| Key | Endpoints |
|---|---|
| `organizers.create` | `POST /admin/organizers` |
| `organizers.update` | `PATCH /admin/organizers/:id`, `POST /admin/organizers/:id/verify` |
| `organizers.delete` | `DELETE /admin/organizers/:id` |

Because they are not in `PERMISSIONS`, no role can ever be granted them, and
they cannot be ticked in the admin Roles screen. Combined with the guard's
`SUPER_ADMIN` short-circuit, the effect is:

> **Only a Super Admin can create, edit, verify or delete an event organizer.
> Admin and Editor get a 403.**

This fails silently rather than loudly — exactly the trap the catalogue exists to
prevent. **Fix:** add the three keys to `PERMISSIONS` and grant them to
`ADMIN`/`EDITOR` alongside `events.*`, then re-seed.

### 5.2 Five `publish` permissions are granted but never checked

`news.publish` **is** enforced — in the service layer at
`articles.service.ts:325`, not via a route decorator. The other five are not
enforced anywhere:

`projects.publish` · `research.publish` · `regulations.publish` ·
`events.publish` · `founders.publish`

For those types, publishing is gated by `<type>.update` instead. So the
"Author cannot publish" rule that holds firmly for news **does not hold** for
Ecosystem, Research, Regulation, Events or Founders — an Author can move any of
those to `PUBLISHED`.

**Fix:** apply the same service-layer check the articles module uses to the other
five content services.

### 5.3 Three permissions have no code behind them

`seo.manage` · `localization.manage` · `ads.manage`

These are grantable and shown in the Roles screen, but no endpoint checks them —
they correspond to the `Redirect`, `Language`/`Translation` and `AdSlot` tables
that have no service layer (see `docs/PROJECT_STATUS.md` §H1). Granting them has
no effect today.

### 5.4 One bad key — fixed

`mail.controller.ts` guarded `POST /admin/mail/test` with `settings.update`,
which is not a real key; the catalogue defines `settings.manage`. That made the
SMTP test button Super-Admin-only. **Corrected to `settings.manage`.**

## 6. Working with permissions

### Reading the current state at runtime

The database is authoritative, not this document:

| Endpoint | Permission | Returns |
|---|---|---|
| `GET /api/v1/roles` | `users.read` | Roles with their current grants |
| `GET /api/v1/permissions` | `users.read` | The full catalogue |
| `PATCH /api/v1/roles/:key` | `roles.manage` | Update a role's grants |

The admin screen is **Staff & Access → Roles & Permissions**.

### Adding a permission

1. Add the key to `PERMISSIONS` in `server/prisma/permissions.ts`.
2. Add it to whichever roles should hold it in `ROLES`.
3. Guard the handler with `@RequirePermissions('your.key')`.
4. Re-seed so the catalogue reaches the database:
   ```bash
   cd server && npm run db:seed
   ```

Skipping step 1 produces exactly the failure in §5.1: a working guard that no
role can ever satisfy.

### Verifying no key has drifted

This is what produced §5. Run it after any permission change:

```bash
cd server && grep -rhoP "@RequirePermissions\(\K[^)]*" src --include=*.ts | tr -d "'" | tr ',' '\n' | sed 's/ //g' | sort -u
```

Compare the output against `PERMISSIONS`. Anything enforced but undefined is a
lockout; anything defined but never enforced is either dead or a missing guard.

## 7. Related protections

Permissions are not the only control in play:

- **Last super-admin guard** (`users.service.ts`) — the final `SUPER_ADMIN`
  cannot be demoted or disabled, so the system cannot be locked out of itself.
- **Audit log** — every privileged mutation is recorded append-only with the
  acting user's id and email, denormalised so an entry stays meaningful after
  the account is deleted.
- **AI agents** carry their own permission list, checked separately
  (`agents.service.ts:219`) against the same key vocabulary.
